# Notes for Claude Code specifically

The `EVIDENCE.md` rules are platform-agnostic. But if your agent runs on Claude Code, a few pieces of this kit map onto features it already has natively — worth using those instead of rebuilding them as files/habits.

**`CLAUDE.md` is already the wake-file mechanism.** Claude Code reads project- and user-level `CLAUDE.md` automatically at session start. Don't build a separate "read this first" convention. Put the rules in `CLAUDE.md` directly, or pull them in with an `@EVIDENCE.md` import line — Claude Code's import syntax actually loads the referenced file's contents. A plain Markdown link does not; it's just text pointing elsewhere, and the target won't be in context unless something opens it. If you want the rules to load automatically, use the `@` import or inline them, not a link.

**Context compaction is a real checkpoint risk, not just restarts.** Claude Code summarizes/compresses older parts of a long conversation automatically as it approaches context limits. That's not a crash, but it's lossy the same way one is: a compacted summary can smooth over a detail ("verified" vs. "assumed to be true") that mattered. Anything load-bearing — a decision made, an artifact's actual location, a claim's grounding type — belongs on disk before compaction happens, not just in the conversation.

**Use the native task tools, not a bespoke queue file.** If the harness exposes task-tracking tools (create/update/list tasks), that's already a more robust version of the "current-tasks.json" idea — integrated with the harness rather than a file the agent must remember to open and parse. One caveat for recovery: picking a task list back up after a fresh launch depends on the right session/list identity being restored, not just on the tools existing. If cross-session continuity matters, confirm how the list is re-addressed on wake — tool availability alone doesn't guarantee it.

**Subagents are the concrete way to do the executor/verifier split.** `EVIDENCE.md`'s non-relay rule says a claim shouldn't become fact just because the same agent that made it also reports it. On Claude Code you can spawn an independent subagent to check a claim in a separate context. But separate context is necessary, not sufficient: the subagent only verifies if you give it an actual acceptance test — the exact command to re-run, the target, the pass condition — and it reports the inspectable result, not a "looks good." A verifier with no test just adds a hop to the relay chain.

**Hooks can enforce parts of this mechanically instead of hoping the model remembers.** If your platform supports lifecycle hooks (session start, after a tool call, on stop), a hook that appends tool calls to an evidence journal is more reliable *for what it covers* than a rule the model has to remember. Know the coverage, though: a post-tool hook typically fires on successful calls (failures are often a separate event), and a crash between the side effect and the journal write still leaves a gap. It logs that a call happened — it does not verify the outcome or block an unsupported "done." Useful as a record, not a guarantee.

**On Cowork specifically:** nothing confident to add beyond the above — it shares Claude Code's underlying session/context mechanics as far as I know, but I don't have grounded specifics on anything unique to it worth stating here. Better to leave this section short than guess.
